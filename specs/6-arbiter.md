# 6-arbiter：集中式总线仲裁引擎

困惑：链式查询为什么离仲裁器近的优先；计数器从 0 计和从中止点计差在哪。学完能对一组按时刻到来的请求排出谁先得到总线。
教材依据：6.3 节，p211–213，图 6.10(a)(b)(c)。教材只有文字，没有数值例；例子都是本站自己出的。
代码：`src/engines/arbiter/model.ts`，入口 `run(params)`；另有 `validateParams`、`schedule(params)`（只算授权，返回 `{ grants: { request, device, at, until }[], never: 请求序号[] }`，grants 按授权先后）、`generate(seed, mode?)`。

## 参数

| 名 | 取值 | 说明 |
|---|---|---|
| `mode` | `链式查询` `计数器定时查询` `独立请求` | 图 6.10(a)(b)(c) |
| `devices` | 2–8 | 设备接口 0 … n−1，接口 0 离仲裁器最近 |
| `requests` | 1–12 项 `{ device, at, hold }` | 设备在总线周期 `at`（0–60 的整数）发请求，要用 `hold`（1–6）个总线周期 |
| `counterFrom` | `0` 或 `中止点` | 计数器定时查询必须给 |
| `priority` | 0…n−1 的一个排列，高到低 | 只用于独立请求，缺省 0 最高 |
| `masked` | 设备号列表 | 只用于独立请求：被屏蔽的请求不响应（p212） |
| `broken` | 设备号 | 只用于链式查询，「弄坏它」：这个接口里传 BG 的电路坏了 |

## 要求

1. 时间以总线周期为单位。总线空闲（BS=0）的时刻 t，在 `at ≤ t` 的未服务请求里仲裁；获胜者从 t 起占用 [t, t+hold)，占用期间不被打断（p211 总线占用期）。同一设备的多个请求按 `at` 先后（再按序号）排队，设备一次只拿出排头那一个。
2. 链式查询：BG 从接口 0 起逐个往下传；到达的接口没有请求就继续传，有请求就截住，置 BS=1（p212）。每到一个接口是一步。
3. 计数器定时查询：计数值逐个发出，与某设备地址相同且该设备有请求时停止，该设备置 BS=1（p212）。`0`：每轮从 0 计；`中止点`：第一轮从 0 计，以后从上次停下的值加 1（模 n）计。每个计数值是一步。
4. 独立请求：排队电路一步选出 `priority` 里最靠前、未被屏蔽且有请求的设备，回它的 BGi（p212）。
5. `broken = b`：BG 到达接口 b 后不再往下传。b 之前没人截住且 b 本身没有请求时，这一轮没人得到总线；b 以后的设备永远得不到总线（p212）。
6. 被屏蔽或在坏点之后的请求不参与仲裁，等别的请求到来；再也没有能参与的请求时结束，列为「得不到总线」。
7. 每次仲裁的步序固定：登记请求（`explain`）、逐个查询（`explain`，独立请求只有一步）、获胜者置 BS（`access`）、用完释放（`explain`）。没人获胜的一轮没有后两步。
8. 状态必须是：`t`；`devices[i]` 有 `br`（这一刻有没有请求）、`bg`（BG 到没到这个接口，独立请求时是 BGi）、`pending`（还在排队的请求数）；`bs`、`owner`、`counter`（不是计数器方式时为 null）、`grants`（已授权的设备号，按先后）。
9. 预测题只在登记请求那一步、能参与的请求来自两台以上设备（或有请求在坏点之后）时出：「这一轮谁得到总线」，选项是有请求的设备，有坏点时加「没有设备」。
10. `table` 列为 次序 | 时刻 | 提出请求的设备 | 查询经过 | 获得总线 | 占用；每行指回置 BS 的那一步（没人获胜的一轮指回最后一个查询步）。
11. `result` 必须有 授权次序、结束时刻（最后一次释放的时刻）、等待合计（各请求从 `at` 到获准的周期数之和）；有得不到总线的请求时加 得不到总线。
12. 参数不合格时 `run` 必须抛出错误，原因与 `validateParams` 相同。

## 场景

- WHEN 链式查询、4 台设备，设备 1、3 都在 t=0 请求 THEN BG 经过接口 0 到接口 1 被截住，设备 1 先得到总线。
- WHEN 计数器、`中止点`，设备 0 和 2 反复请求 THEN 两者轮流得到总线；改成 `0` THEN 设备 0 总是先得到。
- WHEN 独立请求、`priority` 为 [3,2,1,0] THEN 同时请求时设备 3 先得到。
- WHEN 链式查询、`broken = 1`，只有设备 2 请求 THEN 没有设备得到总线，设备 2 列入得不到总线。

## 性质

1. 每个能参与的请求恰好被授权一次，授权时刻不早于 `at`；占用区间互不重叠。
2. 总线空闲而有能参与的请求时一定马上仲裁（不空等）。
3. 链式查询、计数器从 0、独立请求用缺省 `priority` 三者的授权序列完全相同，且每次获胜者是当时有请求的最小设备号。
4. `中止点` 时，获胜者是从上次停点加 1 起按循环次序第一个有请求的设备。
5. 与独立写的朴素参照（逐周期推进）一致；同样参数得到同样 Trace，`validateTrace` 为空。

固定用例：`evals/golden/arbiter-cases.json`，全部手算（链式、计数器两种起点、独立请求带屏蔽、坏链）。
不做：分布式仲裁（6.3.2，留给别的页面）、PCI 隐藏式仲裁、二维（独立请求加链）结构、电路门级时序。

## 待确认

- 「从中止点开始」教材没说是从停下的那个值还是它的下一个值。这里取下一个值：停在 k 后下一轮从 k+1 计。取 k 时刚用完的设备若又有请求会再次获胜，与「优先级相等」不符。
- 坏链时接口 b 自己还能截住 BG。教材只说 b 以后的设备不能工作。
- 同一时刻的仲裁和上一个主方释放总线算在同一周期边界，不另花周期。教材说当前总线业务一结束新主方即接管（p211–212）。
